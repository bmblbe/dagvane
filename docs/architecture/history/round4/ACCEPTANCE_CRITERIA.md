# Критерії приймання (фінальні, Раунд 4C)

**Загальне правило прив'язки:** кожен критерій, що стосується змін коду, верифікується на **точному commit SHA**; верифікаційний запис (лог прогону) містить commit SHA + tree hash і додається до відповідного sign-off. Базлайн-репозиторій: `8e2845dbd780175cbace23f2d9467bdf77d4520a`. «Зелений» = детермінований прогін без мережі, якщо не позначено **[live]** (live-прогони — бюджетовані, поза CI за замовчуванням). Кожен розділ містить негативні тести (N-позначки).

## 1. Milestone 0

**A (правда/транспорт):**
1. E-WIRE: для кожного пункту покриття (`MILESTONE_0_SPEC.md` §4) стаб фіксує очікувані kwargs на межі SDK, включно з кожним continuation-dispatch і конструктором клієнта (`timeout`/`max_retries`).
2. Зафіксований артефакт fail-before-pass: той самий E-WIRE червоний на SHA до фіксу D1, зелений після.
3. Golden-тести 9 команд × обидва entrypoint-и зелені (нормалізація задокументована).
4. `--help` та всі не-SDK команди працюють у venv без `anthropic`.
5. **N:** видалення стаба SDK → `chat` завершується legacy-повідомленням із ненульовим кодом; **N:** E-WIRE ламається (стає червоним) при навмисному поверненні виклику на `cfg["model"]` — тест справді чутливий до регресії.

**B (hardening/докси):**
6. Конкурентний тест: два процеси, що пишуть в одну сесію + один `clear`, — жодного перемішаного/битого рядка, meta консистентна з фактичними записами.
7. Файл із битим JSONL-рядком → рядок пропущено + рівно одне stderr-попередження з лічильником; torn tail → та сама політика; **N:** попередження відсутнє без битих рядків.
8. `umask 000` + `dagvane init` → `secrets.env` має mode 0600 з моменту створення; **N:** повторний `init` не перезаписує наявний secrets; наявний файл із правами 0644 → stderr-попередження при читанні.
9. Метадані вкладення містять і сирий, і resolved шлях (тест із symlink: шляхи різняться і обидва записані).
10. `config set timeout 300` зберігає число; `settings` показує описи `timeout`/`max_retries`.
11. `git check-ignore` підтверджує `.dagvane/runs/`; doc-тести: README-таблиця = ключі `DEFAULT_CONFIG` (11), `16384`; у `DEVELOPMENT.md` відсутні неіснуючі імена функцій; у `project_concept_arch.md` відсутній `messages.create` як опис чинного шляху.
12. **N:** `LICENSE`, ліцензійні рядки README/pyproject байт-незмінні відносно базлайну (рішення власника не узурповано).

## 2. Перший зріз (`council-v1`)

1. 100% council-логіки проходить на FakeBackend без мережі; той самий план виконується на змішаних маршрутах конфігурацією, без зміни коду.
2. Структурний анти-анкоринг: контекст кожного propose-вузла зібраний **тільки** з його InputManifest; **N:** інʼєкція sibling-фрагмента в маніфест-фікстуру ловиться тестом (перевірка InputManifest, не промпт-тексту).
3. Реальне часове перекриття propose-спроб зафіксоване подіями (паралельність, не серіалізація).
4. Бар'єр жорсткий: жоден review не стартує до термінальності всіх propose; само-рецензія структурно неможлива (PlanValidator-тест); sealed-анонімізація: mapping відсутній у контекстах рецензентів, наявний у маніфесті run.
5. Провал однієї пропозиції → run завершується `failed` із діагностикою; **N:** тиха деградація до одно-кандидатної «ради» неможлива.
6. Malformed Decision від судді → рівно одна budgeted repair-спроба → гучний fail; схема Decision валідована; RunReport існує для **кожного** run (включно з failed/cancelled); Decision — лише для judged-планів.
7. Бюджет: TOCTOU-тест (конкурентні admission під lock не перевищують cap); кожен фізичний dispatch має власні `operation_id`/`call_id`/receipt/резервацію; **N:** форсована помилка 500 → application-retry з новим `call_id`, новою резервацією, тим самим `operation_id`; **N:** grep-тест конструкції engine-клієнта: `max_retries=0` (SDK-retry заборонений).
8. Budget-exhaustion посеред run → `budget.exceeded`, граційне завершення, часткові артефакти збережені, RunReport присутній.
9. Wire-digest: receipt ↔ надісланий запит ↔ персист збігаються хешем; `capture_layer` чесно позначений.
10. Редакція секретів: сідований ключ → нуль збігів у каталозі run, stdout, артефактах.
11. Стан-машина: golden-послідовності подій для completed/failed/cancelled; термінальна подія — остання durable-подія інвокації.
12. **[live]** Реальна рада на ≥2 вендорських сімействах через ≥2 маршрути в жорсткому бюджеті; звіт usage/cost звірений із receipt-ами. Fake-прогін доказом live-критерію не є.

## 3. Другий зріз (`solo-patch`)

1. Ізоляція: після повного циклу головне дерево незаймане (`git status --porcelain` порожній), зміни лише в worktree/гілці кандидата.
2. Per-worktree venv: «тінення» editable-install виключене (тест: конфліктна версія в головному venv не видима у verify); провізіювання wheel-кешу робить `pip --no-index` успішним; **N:** без провізіювання установка чесно падає (не тихо тягне мережу).
3. Committed-state: перед verify/review porcelain порожній; untracked після кроку → commit або fail вузла; **N:** `git add -A`/`clean -fdx` недоступні агенту (інструмента не існує; спроба через apply_patch до `.git` — відмова).
4. Реконсиляція патча: чотиригілкова процедура (`ARCHITECTURE_DECISION.md` §11) покрита тестами всіх чотирьох виходів; **N:** сторонні зміни у worktree → `effect.uncertain`, автоповтору немає.
5. ASK-механіка: `apply_patch` без гранта → `permission.request` → `run.blocked` → exit-код 20; `resume --grant apply_patch` у **новому процесі** продовжує run; **N:** `--grant` не розв'язує `effect.uncertain` (потрібен `--resolve`).
6. Рев'ю: вхід рецензента = diff + verify-звіт + immutable TaskSpec; **N:** план без TaskSpec-входу для review-вузла відхиляється PlanValidator.
7. Двофазний integrate: M будується на scratch-ref; verify(M) зелений із зафіксованими SHA/tree-hash; approval-digest покриває {T_old, M, taskspec, diff, verify, review}; CAS-фліп; постумова target==M; **N:** зрушений target → STALE і перебудова M; **N:** `--approve-digest` з невірним хешем → відмова; **N:** мутація дерева тестом інвалідовує verify (tree-hash mismatch).
8. Rollback: задокументований `git revert -m 1 M` відпрацьований тестом, подія записана.
9. **[live]** Мала реальна зміна нативним кодером у скінченному бюджеті, повний цикл до target==M — лише після закритих E-WT/E-SBX.

## 4. IPC-контракт

1. `--output ndjson`: stdout містить **лише** валідні NDJSON-кадри (парсер-тест на 10 000+ подій); stderr-шум не з'являється в stdout; кожен кадр ≤1 MiB; **N:** подія з надрозмірним payload → artifact ref, не роздутий кадр.
2. Байт-ідентичність: кожен durable-кадр stdout байтово дорівнює своєму журнальному рядку; durable-кадри інвокації — префікс її журнального сегмента.
3. kill -9 посеред потоку: stdout ≤ журнал (ніколи не випереджає); після `resume` перший durable-кадр — `run.resumed{last_seq}`; `dagvane events --since <seq>` повертає пропущені канонічні байти; конкатенація (клієнтський реплей) байт-еквівалентна журналу.
4. Скасування: SIGTERM → `run.cancelling` → термінальна `run.finished{status:cancelled}` **останнім** кадром; після неї жодних подій; **N:** незавершений reap → `status:failed, reason:cleanup_incomplete` (не «cancelled»).
5. Exit-коди відповідають таблиці (0/2/10/20/30/40); blocked-run → 20 і відновлюваний.
6. Text-рендерер: детермінований replay golden `events.jsonl` → байт-ідентичний вивід (CI-контракт); невідомий тип події → must-ignore із журналюванням пропуску, без падіння.
7. Контракт заявлений лише для POSIX/Linux (документаційний тест).

## 5. Безпека tools/worktree/процесів

1. Контейнмент: traversal-набір (`..`, absolute, symlink-компонент, symlink-escape на файл поза worktree) → відмова для read_file/search/apply_patch; підтверджено використання openat2/dirfd-механізму (юніт із symlink-підміною між перевіркою і відкриттям — відмова).
2. Заборонені цілі патчів: `.git/`, `.dagvane/` → відмова.
3. Env-scrub: env дочірніх процесів verify не містить `*_API_KEY` (сідований ключ у батьківському env відсутній у дампі env дитини); HOME/XDG — синтетичні.
4. Process-групи: verify з таймаутом убиває **все** дерево (тест із дитиною-що-спавнить-онука); 20 kill-циклів → нуль зомбі/сиріт.
5. rlimits: дочірній процес, що перевищує ліміт RSS/CPU, завершується, verify звітує це чесно.
6. Sandbox-політика: без доступного механізму і без винятку → `verify.refused{no_sandbox}`, run blocked (**fail-closed**); **N:** із `--sandbox-exception=trusted-project` → виконання дозволене, durable-подія з чесним маркуванням присутня в журналі; **N:** подія-маркування відсутня → тест червоний.
7. Fencing: процес зі застарілим fencing-token (симульований takeover) отримує відмову на мутації/CAS; flock звільняється при смерті процесу (kill -9 → новий процес захоплює lease без ручного втручання).
8. Секрети: сідований ключ → нуль збігів у всіх артефактах run, журналі, stdout (обидва зрізи).

## 6. Resume і fault-injection

1. kill -9 на кожній фазі council і develop (матриця точок ін'єкції): після процедури відновлення журнал — валідний префікс (torn tail обрізаний зі збереженою копією `*.torn-*`), seq gapless, `resume` завершує run без подвійного застосування host-ефектів.
2. Crash між intent і result для кожного класу ефекту: LLM → billed-but-lost за стелею + новий dispatch (той самий `operation_id`); git → чотиригілкова реконсиляція; неідемпотентний tool → park; **N:** жоден шлях не робить мовчазний автоповтор ефекту з невідомим результатом.
3. Spend переживає resume: сума committed до і після crash монотонна; резервації in-flight на момент crash закриті за стелею; **N:** seq не перевикористовується після resume (перевірка унікальності по всьому журналу).
4. Blocked-run переживає рестарт: `permission.request`/`effect.uncertain` персистентні; resume у новому процесі з новим PID продовжує коректно.
5. Fresh-process replay термінального run відтворює фінальний стан (статуси вузлів, artifact-хеші) без мережі.
6. Артефакти: crash одразу після rename, до події → blob без референсу (допустимо), подій-сиріт (референс без blob) — нуль; порядок fsync підтверджено інструментальним тестом запису.
7. Годинники: parked-час не споживає active-runtime cap (тест зі штучною паузою blocked >кап-у).

## 7. Конформанс провайдерів

1. E-CONF council-tier для профілю OpenAI зелений на фікстурах (messages, streaming, usage, нормалізація помилок, скасування посеред стріму з чесним обліком); фікстури pinned (SHA зафіксовано у верифікаційному записі).
2. «Підтримуваний» статус профілю видається **лише** за пройденим tier-ом; **N:** непройдений профіль (DeepSeek/OpenRouter/Ollama до своїх tier-ів) у продуктовому `routes.json` → `routes check` червоний (позначка experimental обов'язкова).
3. Ґратка EffectiveCaps: юніт-тести — unknown → deny; числові мінімуми; несумісна схема → deny; **N:** запит із параметром поза EffectiveCaps (напр. `top_k` на маршруті без нього) → гучна помилка-подія, **не** мовчазний drop і не мовчазна відправка.
4. Рівні доказовості: продуктовий маршрут із фактично використовуваною capability рівня нижче conformance-tested → відмова PlanValidator; авто-підвищення рівня неможливе (немає такого коду-шляху).
5. Quirk-журнал: кожен виявлений quirk класифіковано severity; критичний (облік/скасування/безпека/цілісність) → зафіксоване рішення про діалект; **N:** негативні фікстури (malformed usage, відсутній finish_reason, обрив стріму) не приводять до мовчазного «успіху».
6. Anthropic-паритет: нормалізований StopReason і цикл продовжень дають той самий видимий результат, що й legacy (характеризаційне порівняння на фікстурах).

## 8. Bootstrap exit

Усі пункти перевіряє `dagvane exit-check` (машинний валідатор) на фінальних SHA; звіт додається до sign-off.

1. **Дві послідовні зміни:** base₂ == M₁ (merge-коміт першої зміни); перевірка git-предків; **N:** будь-який коміт між M₁ і base₂ → fail (заборона ручного «підремонтування» ядра між runs); зміни реального коду: diff кожної торкається `*.py` двигуна; ≥1 зміна торкається шляхів оркестраційного ядра, перелічених у TaskSpec; **N:** docs-only diff → відхилено механічно.
2. **Пререєстрація:** TaskSpec-хеш і хеш regression-оракула записані в маніфест run **до** першої події виконання; **N:** пост-фактум доданий оракул (хеш не збігається) → fail.
3. **Оракул fail-before/pass-after:** acceptance-тест червоний на base і зелений на M — обидва прогони зафіксовані; **N:** оракул, зелений уже на base, → fail.
4. **Повний цикл усередині Dagvane:** журнал доводить: рада ≥2 сімейств через ≥2 маршрути → `decision.json` → імплементація нативним `DagvaneAgentWorker` → verify на exact SHA → незалежне рев'ю (інша модель, ніж кодер) з TaskSpec → approval-digest → CAS → target==M; людські дії — лише формулювання Task/acceptance, гранти і hash-bound integrate.
5. **Crash/resume:** в одному з двох runs — інжектований kill -9 + resume новим процесом; exit-check підтверджує: кожен фізичний dispatch має receipt і резервацію; host-ефекти — exactly-one (записи реконсиляції); spend монотонний; **окремий розділ звіту перелічує всі неоднозначні провайдерські виклики** (може бути порожнім).
6. **Replay і provenance:** fresh-process replay відтворює термінальний стан і artifact-хеші; маніфест містить base/tested(M)/merged SHA, версії engine/Python/залежностей, хеші промптів/роутів/вхідних артефактів, usage/budget-звірку (капи дотримані); сідований секрет-скан — нуль збігів.
7. **Нуль ручного relay:** аудит журналу — всі міжвузлові передачі через RunStore/InputManifest refs; відсутність зовнішнього супервізора журнал довести не може — фіксується процедурною атестацією оператора (артефакт у маніфесті run).
8. **Процедурне заміщення:** черговий реальний дизайн-раунд Dagvane проведено через `dagvane council` (ізоляція, бар'єр, sealed-анонімізація, provenance-хеші); позазнімковий тулінг раундів для цього не використовувався (атестація).
9. **N (валідатор):** навмисно зіпсований будь-який хеш маніфесту → exit-check червоний із точною діагностикою.

Автономний merge **не** є умовою exit; людський integrate-гейт — норма.
